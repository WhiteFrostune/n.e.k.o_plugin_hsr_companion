# S1 瓶颈分析与 A–D 方向对照（2026-11-22）

基线：`bb1838d9c4dc31f1c8d11c0bff7ec39ee38852e4`，分支 `codex/0.9.8-s1-current-regions-20261121`。
本轮只新增本报告和 `scripts/analyze_ocr_bottlenecks.py`。产品代码、安装版、问题等待期限和姓名门槛不变；未调用游戏、视觉助手或安装版服务，未推送。

## 结论先行

1. 已定位本次约 4.9 秒的主要成本：**首次区域文字检测**，不是姓名单行复核。856×384 拼图进入检测器后会被放大为 1632×736；这轮检测的预处理、推理、后处理都明显耗时。
2. 上轮 1–2 秒与本轮 4.9 秒不能直接作为回归判断。本轮重放旧截图也需要 5.54–6.20 秒；同图同模型同配置下，历史运行环境没有 CPU/库文件指纹记录，**无法追溯证明历史差值全部由哪一个因素造成**。没有证据支持又增加一次 OCR 或姓名确认变严。
3. 后台 full 并非只在画面变化时运行。未变画面仍有四秒兜底以及未稳定等触发条件；每次 full 又占数十秒，实际常驻负担远高于“偶尔巡逻”的直觉。
4. 单独做 A 无法跳过正在执行的原生调用；B 去掉锁等待但仍有原生检测成本；C 可以停止真实原生进程，但重启代价显著；D 最值得优先减少稳定页面的无效工作，但不能无限保鲜旧事实。
5. 推荐 **D 为主、A 收好交接和核验生命周期**；若需要移动画面下的确定性查询隔离，再选择 B。C 后置用于真正的硬中断/卡死治理。此推荐不代表 A+D 已达到任何秒数 SLO。

## 1. 证据与测量方法

真实部分：生产区域读取、检测/识别模型、姓名确认、bb1838d 时间线、正式工具入口和常驻 `_observer_loop`。
替代部分：保存帧转 BMP、内存 SDK 存储、关闭真实消息目标。B 是两个独立 `LocalVisionAdapter` 的原生并行原型；C 是自有子进程原型，均不是已接入产品的方案。

保留的本机数据位于 `E:/code/neko2/logs/s1-bottleneck-analysis-20261122/`：

- `paired.json`：首批细粒度采资源，存在明显测量扰动，**不用于延迟估算**。
- `controlled-v2.json`：低扰动对照与 B；其中旧 C 部分测错启动器 PID，**不用作 C 证据**。
- `process-corrected.json`：修正 C，握手实际解释器 PID 并校验是本次 Popen 的子进程，然后才终止该 PID。
- `unchanged-patrol.json`：生产观察循环在完全相同像素下的两轮 full。
- `methodology-notes.json`：无效/受扰动样本的标记和原因，原记录均保留。

资源采样仅在整轮外层开一个采样线程，内部阶段只记时间和进程 CPU 计数，避免为每个阶段再开采样线程。CPU 时间包括同进程所有并行线程，分段存在嵌套，**不可相加**。1 核等价=100% 单逻辑核，机器共 16 物理核/32 逻辑核；工作集 RSS 与私有提交分别列出，不混称物理内存。

C 的前一版错误：Windows venv 的 Popen PID 是启动器，约 6 MiB，不能代表真正模型进程，也不能证明原生推理被停止。已废弃此前约十毫秒的停止结论；正确复测是约 0.10 秒。

## 3. 后台 full 现在怎样巡逻

源码依据：`__init__.py:1255` 的 `should_push`，`1377` 的完成时间更新，`1417`附近的0.25秒循环；`assistant_runtime/server.py:234`附近的0.75秒采集节拍。

- 助手通常每约0.75秒尝试独立采集，采集与 full OCR 不是同一频率。
- 观察循环约每0.25秒检查一次，但执行 full 时同一循环要等待它。
- 换页/依赖挑战、查询/待办、未稳定状态超过1.5秒、差异超过条件且超过2秒等，会更早触发。
- 即使无明显变化，完成上次提交后超过4秒仍会触发下一轮 full。不是“每4秒就能完成一轮”，也不是“图不变永久不扫”。
- 只关主动讲话不会自动停 full；观察仍负责面板和按需查询的候选。

未变像素的真实生产循环重放：

| 项目 | 第1轮 | 第2轮 |
| --- | ---: | ---: |
| full原生开始 | 0.591秒 | 38.140秒 |
| full原生结束 | 34.707秒 | 68.094秒 |
| 原生耗时 | 34.116秒 | 29.954秒 |
| 完成提交 | 36.141秒 | 69.946秒 |

两次 full 开始相隔约37.55秒，两次提交相隔约33.80秒。全程像素相同、61次取帧，约69.95秒消耗116.06 CPU秒（1.66核等价）。第二轮距上次提交仅约2秒，说明更早触发分支也可能起作用；本轮未单独记录具体OR分支，不把它硬解释成四秒兜底。该测试足以否定“未变化就不再扫”。

单独原生 full 试验约27.51秒、42.69 CPU秒；生产循环多了现场审核/检查点及运行条件，因此不能把27.51秒当所有场景的完整轮次耗时。

### A/D 的可复现反事实算式

使用原生full27.511秒及其中不可中断的调用块9.905、5.359、7.916、3.049秒。假设提问均匀落在稳定巡逻周期、旧核验不再拖住、查询原生中位4.783秒，则期望残余等待为 `sum(block²/2)/(full+gap)`：

| 完成后的gap（仅方案参数） | 模型占用比例 | 平均原生残余等待 | 原生查询+残余（还没加包装） |
| --- | ---: | ---: | ---: |
| 4秒 | 87.3% | 3.154秒 | 7.937秒 |
| 15秒 | 64.7% | 2.338秒 | 7.121秒 |
| 60秒 | 31.4% | 1.136秒 | 5.919秒 |

这不是实测分布/成功率，也没有模拟业务事件到达；生产完整轮次也更长。算式说明：**把4秒改15秒只减少约0.82秒期望残余，不能把数十秒full变成便宜巡逻**。稳定画面跳过无必要full，比只小幅降频更有意义。60秒只是反事实对照，不推荐作为战斗事件侦测节拍。

本轮各方向都没有证明“稳定1–2秒”或“拿锁后每次4.5秒内确认”。第一次检测的成本仍在，方案选择必须承认这个下限。

## 6. 推荐组合与边界

推荐先选 **D+A**：保留连续独立采集与页面/对象变化保护；稳定页面不重复full，提问按需求读；同时明确旧核验何时仍有价值、何时应结束，减少一个请求内部的重复工作。不增加模型、不换分流或问法规则、不放松姓名/数字验证。

若目标是“画面正在变化、full正在运行时提问也能尽快开始”，D+A不能保证，应另选 **B** 做完整正式链原型与资源预算验收。B这次额外常驻内存较小，但5.6–6.3秒的原生读取已说明它不能承诺1–2秒。

C先后置。它有真正的可终止边界价值，但21秒重热身、独立进程资源、IPC/旧帧收回都属于更大范围；不要为了绕一个锁直接把整个流程升级成多进程系统。

以上仅供用户选方向，未实施任何候选。USER_CONTEXT_GET、模型网络等待、表达、遗器规则和配队未扩修。存档配队继续不要求实时读屏。
